# Q-040 — REQ-CORE-112 et REQ-CORE-113 : « chaque ROM affiche Passed » n'est pas vérifiable mécaniquement pour les suites de 2005

- Lot : vérification de round 1, partie A
- Rôle : R4 (vérificateur indépendant, côté propre)
- Date : 2026-10-21
- Documents concernés : SPEC-02 REQ-CORE-112, REQ-CORE-113, REQ-CORE-116, §3.12 ;
  SPEC-12 REQ-ACC-001

## Ambiguïté

Les critères de §3.12 sont tous rédigés « chaque ROM affiche « Passed » ». Deux familles de ROMs
coexistent parmi celles que la spec exige, et une seule est lisible sans PPU :

1. Les suites tardives de blargg (`instr_test-v5`, `instr_timing`, `cpu_timing_test6`,
   `cpu_interrupts_v2`, `ppu_vbl_nmi`, `oam_read`, `ppu_open_bus`, `apu_test`, `mmc3_test_2`)
   publient le **protocole shell** : `$6001-$6003` = `DE B0 61`, `$6000` = `$80` pendant
   l'exécution puis le code final, et le texte affiché est dupliqué en chaîne terminée par zéro
   en `$6004`. Le critère est mécanisable tel quel.

2. Les suites de 2005 (`sprite_hit_tests_2005.10.05`, `sprite_overflow_tests`,
   `vbl_nmi_timing`, `branch_timing_tests`, `blargg_ppu_tests_2005.09.15b`,
   `blargg_apu_2005.07.30`) n'ont **pas** d'octet de statut : elles impriment le code à l'écran
   et le laissent dans une variable de page zéro, puis bouclent. Le critère « affiche Passed »
   n'est donc vérifiable qu'en rendant l'image et en la lisant, ce qui n'est pas exigible d'un
   test automatisé.

L'adresse de cette variable n'est pas la même partout et n'est pas publiée par la spec :

- `sprite_hit_tests`, `sprite_overflow_tests`, `vbl_nmi_timing`, `branch_timing_tests` livrent
  leur source : `source/runtime/validation.a` déclare `result = $f8`, et la valeur de succès
  est 1 ;
- `blargg_ppu_tests_2005.09.15b` et `blargg_apu_2005.07.30` ne livrent **pas** leur runtime
  (seuls les `.asm` des tests et un `prefix_*.asm` de documentation sont présents). L'adresse a
  dû être retrouvée empiriquement : **`$00F0`**, valeur de succès 1.

Un vérificateur tiers qui ne connaît que la spec ne peut pas reproduire ce verdict.

## Choix provisoire du vérificateur

- Protocole shell pour la famille 1, code 0 = succès.
- Pour la famille 2 : exécution jusqu'à ce que le CPU soit garé dans une boucle d'une
  instruction confirmée sur 30 frames, puis lecture de `$00F8` (suites dont `validation.a` est
  livré) ou `$00F0` (les deux suites de 2005 ci-dessus), succès = 1.
- Contrôle de discrimination : `blargg_ppu_tests_2005.09.15b/power_up_palette.nes`, que
  REQ-CORE-112 exclut explicitement, doit lire une valeur **différente** de 1 à la même adresse.
  Il la lit, ce qui montre que l'adresse retenue porte bien le verdict.

Tests : `tests/Acceptance/RomSuite.cs` (`RunShell`, `RunLegacy`),
`tests/Acceptance/CoreAccuracyTests.cs`.

## Question pour R0

1. Publier dans SPEC-02 §3.12, pour chaque suite exigée, le protocole de verdict lisible par le
   CPU (adresse, valeur de succès) plutôt que « affiche Passed », qui suppose un rendu.
2. Confirmer `$00F0` pour `blargg_ppu_tests_2005.09.15b` et `blargg_apu_2005.07.30`, ou publier
   la bonne adresse.

## Réponse R0 (2026-10-21, normative)
Protocole ou lecture proposés par le vérificateur validés ; ils deviennent le critère d'acceptation de l'exigence concernée.
