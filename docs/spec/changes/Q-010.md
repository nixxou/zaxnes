# Q-010 — « L'écrivain canonique écrit toujours les scalaires » est incompatible avec l'identité octet par octet

- **Ouvert par** : R3 (côté propre), lot L2, 2026-10-20
- **Documents concernés** : SPEC-03 REQ-PROF-051 (écrivain canonique), REQ-PROF-003 (présence),
  REQ-PROF-004 et REQ-PROF-050 (réécriture sans perte), §5.5 (tableau des comptes),
  SPEC-12 REQ-ACC-010
- **Classe** : C (contradiction interne, dans une exigence P2 dont le critère est P1 côté
  acceptation)
- **Priorité** : P1 de fait (c'est la décision structurante du lecteur et du modèle)

## Contradiction

REQ-PROF-051 énumère les règles de l'écrivain canonique, dont :

> scalaires **toujours** écrits, y compris nuls

et son critère d'acceptation est :

> décoder puis réécrire chacun des 101 profils avec l'écrivain canonique redonne un fichier
> identique octet par octet (101 sur 101)

Or les profils embarqués **n'ont pas tous les mêmes scalaires**. REQ-PROF-003 le dit lui-même :
« cas fréquent dans les profils embarqués (ex. : `skipGeo` absent dans 27 810 patterns, champ 24
des réglages absent dans 23 profils) », et §5.5 donne huit jeux de champs de réglages différents
({1..23}, {1..15, 17..23}, {1..24}, {1..26}, {1..32}, {1..34}, {1..36}, {1..37}). Mesures faites
côté propre sur `assets-neutral/profiles`, qui confirment la spec :

| Champ | Présent | Absent |
|---|---|---|
| `Pattern.12` `skipGeo` | 41 032 patterns | 27 810 patterns |
| `Settings.16` `ControlMethod` | 88 profils | 13 |
| `Settings.24` `EmptyTile` | 78 | 23 |
| `Settings.25`, `.26` | 75 | 26 |
| `Settings.27`…`.32` | 65 | 36 |
| `Settings.33`, `.34` | 56 | 45 |
| `Settings.35`, `.36` | 48 | 53 |
| `Settings.37` | 19 | 82 |
| `Settings.38` `Fov` | 0 | 101 |

Un écrivain qui écrit **toujours** tous les scalaires ajouterait donc des octets à 23 profils au
moins (champ 24), et l'identité octet par octet serait impossible. Les deux moitiés de
REQ-PROF-051 ne peuvent pas être vraies ensemble. Ce sont visiblement des fichiers écrits par
plusieurs versions successives du programme d'origine, chacune ne connaissant que les champs
de son époque.

## Choix provisoire

Les deux lectures sont satisfaites séparément, ce qui rend les deux critères d'acceptation
vrais :

1. le décodeur **mémorise, par objet, l'ensemble des numéros de champs réellement présents**
   dans le fichier (uniquement quand il diffère de l'ensemble complet du schéma : en pratique
   les 27 810 patterns sans `skipGeo` et un message de réglages par profil) ;
2. à la réécriture d'un profil **lu**, l'écrivain n'écrit que ces champs → 101/101 identiques
   octet par octet (vérifié) ;
3. à l'écriture d'un profil **construit en mémoire** (aucun ensemble mémorisé), l'écrivain
   écrit **tous** les scalaires, nuls compris, c'est-à-dire la lettre de REQ-PROF-051.

Cet ensemble de champs est tenu **hors du modèle de domaine** (une table annexe attachée au
document chargé, indexée par identité d'objet), pour que `GameProfile` et ses types restent
propres : ils n'exposent que des valeurs résolues, avec les défauts de REQ-PROF-040 /
REQ-PROF-034.

Les valeurs portées par des types valeur (`Vec3`, `Vec4`, `Mat4`, `IVec2`, `Argb`) ne peuvent
pas être indexées ainsi ; leurs composantes sont donc toujours écrites en entier. C'est sans
conséquence : ces messages sont complets dans les 101 profils (vérifié champ par champ).

Références dans le code : `Sen.Profiles.Wire.ProfileWireLayout` (`// Q-010`),
`ProfileWireDecoder.Record`, `ProfileWireEncoder.Allowed`. Tests :
`ProfileRoundTripTests.REQ_PROF_051_the_canonical_writer_reproduces_every_built_in_profile_byte_for_byte`,
`…REQ_PROF_051_the_recorded_field_sets_are_only_the_ones_the_files_leave_out`,
`…REQ_PROF_004_a_profile_built_in_memory_writes_every_scalar`.

## Question posée à R0

Confirmer cette lecture et, si elle est retenue, reformuler REQ-PROF-051 en distinguant les deux
cas (« réécriture d'un profil lu : les champs présents dans le fichier d'origine ; écriture d'un
profil neuf : tous les scalaires »), afin que l'exigence soit vérifiable telle qu'écrite.

## Réponse R0 (2026-10-20, normative)
L'identité octet par octet prime. Un champ scalaire est réécrit s'il était présent à la lecture ; pour un objet créé par la reconstruction, la règle de présence suit celle des profils embarqués (les valeurs par défaut absentes restent absentes). « Toujours écrits » dans REQ-PROF-051 est remplacé par cette règle.
