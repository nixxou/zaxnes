# Q-007 — MMC5 : quel jeu de banques CHR pour les enregistrements de tiles ?

- **Ouvert par** : R3 (côté propre), lot L1d, 2026-10-20
- **Documents concernés** : SPEC-02 REQ-CORE-037, REQ-CORE-038, REQ-CORE-041, REQ-CORE-039,
  REQ-CORE-033, REQ-CORE-100 (ligne « 5 | MMC5 »)
- **Classe** : C (ambiguïté)
- **Priorité** : P2 (n'affecte que les jeux MMC5 en mode sprites 8×16 ; aucun n'est cité
  comme point sensible par REQ-CORE-115)

## Ambiguïté

REQ-CORE-037 et REQ-CORE-041 décrivent l'état utilisé pour construire un enregistrement comme
« les banques CHR en vigueur » au moment de la capture. Sur toutes les cartes exigées sauf une,
cette expression est univoque : il n'existe qu'une table de banques CHR à un instant donné.

Le MMC5 en possède **deux** (wiki nesdev, « MMC5 ») :

- `$5120`-`$5127`, utilisé pour les récupérations de motifs de **sprites** ;
- `$5128`-`$512B`, utilisé pour les récupérations de motifs de **fond**.

La règle matérielle est : quand PPUCTRL sélectionne des sprites 8×16, les deux jeux servent
séparément (fond ← `$5128`, sprites ← `$5120`) ; sinon, le dernier jeu écrit sert pour tout.
Un même instant peut donc présenter deux banques différentes à la même adresse CHR selon la
nature de la récupération, et la question « quelle banque est en vigueur » n'a pas de réponse
unique.

La tension est avec deux autres exigences :

- **REQ-CORE-039** demande que le motif d'un enregistrement soit « celui que le matériel
  afficherait pour cette tile sur la ligne de capture ». Pour un MMC5 en 8×16, cela impose
  deux jeux différents selon que l'enregistrement est de fond ou de sprite.
- **REQ-CORE-033** interdit tout effet de bord à la lecture. Le choix du jeu n'en produit
  aucun : c'est bien une question de *valeur lue*, pas d'effet de bord.

## Choix provisoire

Le chemin de lecture inerte reçoit la **nature de la récupération** (fond ou sprite), et le
MMC5 applique la règle matérielle :

- enregistrements de fond → `$5128`-`$512B` en mode 8×16, dernier jeu écrit sinon ;
- enregistrements de sprite → `$5120`-`$5127` en mode 8×16, dernier jeu écrit sinon.

C'est la lecture conforme à REQ-CORE-039. L'autre lecture possible (un seul jeu, celui des
sprites, pour tous les enregistrements) serait plus simple pour un cœur qui ne connaîtrait
qu'une table de banques, mais afficherait les mauvaises tiles de fond dans les jeux MMC5 à
sprites 8×16.

Non implémenté, et hors du minimum exigé par REQ-CORE-100 (ExRAM et attributs étendus en P2) :
le **mode d'attributs étendus** du MMC5 (`$5104` = 1), où chaque tile de fond tire sa banque de
4 Kio et sa sous-palette d'un octet d'ExRAM. Si R0 veut que les lots en tiennent compte, il
faudra préciser dans REQ-CORE-038 ce que devient le champ `palette` d'un enregistrement dans ce
mode (la sous-palette vient alors de l'ExRAM et non de la table d'attributs).

Références dans le code : `ChrFetch`, `Cartridge.PpuRead(ushort, ChrFetch)`,
`Cartridge.PpuPeek(ushort, ChrFetch)`, `Mmc5.ChrAddress`,
`Ppu2C02.ReadPatternPlanes`. Tests :
`MapperTests.REQ_CORE_100_mmc5_serves_background_fetches_from_the_second_set_with_tall_sprites`.

## Question posée à R0

Confirmer la règle « le jeu de banques suit la nature de la récupération », ou imposer un jeu
unique pour tous les enregistrements. Préciser, le cas échéant, le comportement attendu du
champ `palette` en mode d'attributs étendus.

## Réponse R0 (2026-10-20, normative)
Pour les **enregistrements de tiles** (REQ-CORE-037/039/041), le motif est lu dans une **table de banques CHR unique** : chaque écriture dans l'un ou l'autre jeu de registres CHR du MMC5 met à jour cette table, et la dernière écriture l'emporte, même en mode sprites 8×16. C'est le comportement de la référence, avec lequel les profils ont été construits (fidèle). Le rendu en pixels du mode 2D PEUT suivre la règle matérielle exacte (deux jeux en 8×16) ; l'écart éventuel entre les deux n'est pas un défaut.
