# Q-083 — `AMD-049` : le critère sRGB d'albédo nul (21 ; 5) ne vaut pas pour « la même configuration » que les deux vecteurs linéaires

Rôle : R3 (côté PROPRE) | Date : 2026-10-31 | Lot V2-9 (mise en œuvre de `REQ-SCN-075`)
Documents concernés : `spec/changes/AMD-049-eclairage-backdrop.md` v1.1 §2 (3ᵉ critère d'acceptation)
et §3 point 2 ; `R2-review-AMD-049.md` §1.1, §1.4, point 49-3 ; `SPEC-06` `REQ-SCN-025`,
`REQ-SCN-027`, `REQ-SCN-031`, `REQ-SCN-048`.

## 1. L'incohérence

`REQ-SCN-075` donne trois critères d'acceptation automatiques :

1. **linéaire, ±0,001** — `N = (0, 0, −1)`, `V = (0, 0, −1)`, `Light.Direction = (0, 0, 1)`,
   lumière blanche d'intensité 1, hors ombre : `nl = nv = nh = lh = 1`, et pour `c = 0,2` la
   couleur vaut 0,2372 ;
2. **linéaire, ±0,001** — la même configuration dans l'ombre (`s = 0,2`) : 0,0753 ;
3. **sRGB 8 bits, ±2** — « **même configuration**, albédo nul : sRGB (21, 21, 21) hors ombre,
   (5, 5, 5) dans l'ombre ».

Le §3 point 2 donne les **mêmes chiffres** mais pour une **autre** lumière : « un panneau presque
noir (sRGB ≈ 21 hors ombre, ≈ 5 dans l'ombre, **avec la lumière par défaut** et l'intensité 1) ».
La lumière par défaut de `REQ-SCN-025` est `(1, −1, 1)`, pas `(0, 0, 1)`.

Or le modèle dépend de la direction de la lumière par `nl`, `nh` et `lh`, et pour un albédo nul il
ne reste que le terme additif `s · E · Spec · F`, qui n'est pas le même dans les deux cas :

| Configuration | `nl` | `lh` = `nh` | `Spec · F` | sRGB hors ombre | sRGB dans l'ombre |
|---|---|---|---|---|---|
| **`Light.Direction = (0, 0, 1)`** (celle des critères 1 et 2) | 1 | 1 | 0,0104104 | **26** | **7** |
| **`Light.Direction = (1, −1, 1)`** (défaut, §3 point 2) | 0,57735 | 0,88807 | 0,0075352 | **21** | **5** |

Détail du second cas (vue frontale, `V = (0, 0, −1)`) : `F90 = 2,061563`, `Fd = 1,014316`,
`Vis = 0,318746`, `D = 0,325699`, `Spec = 0,188302`, `F = 0,0400169`, d'où `Spec · F = 0,0075352`,
`srgb(0,0075352) × 255 = 21,07` et `srgb(0,2 × 0,0075352) × 255 = 4,97`. Le premier cas donne
`Spec · F = 0,2602538 × 0,04 = 0,0104104`, `srgb(…) × 255 = 26,13`, et dans l'ombre
`0,2 × 0,0104104 = 0,00208208`, sous le coude de la courbe sRGB, donc `× 12,92 × 255 = 6,86`.

Les deux lectures diffèrent de **5 niveaux hors ombre et 2 dans l'ombre**, au-delà de la tolérance
de ±2 du critère : il n'est pas vérifiable sous les deux lectures à la fois.

L'entrée de `journal/JOURNAL.md` qui accompagne le passage d'`AMD-049` en v1.1 (2026-10-31 06:30)
annonce d'ailleurs « critère `REQ-SCN-048` réécrit ; **albédo nul recalculé sRGB 26/7** » : la
valeur 26/7 était donc bien celle visée pour ce critère, mais le §2 de l'amendement porte toujours
21/5. Il s'agit selon toute vraisemblance d'une correction annoncée mais non reportée dans le
texte — ce qui, si c'est le cas, rend la réponse à la question 1 du §3 immédiate.

`R2-review-AMD-049` ne lève pas le doute, et le confirme plutôt : son §1.1 recalcule les deux
vecteurs linéaires avec `L = (0, 0, −1)` et ne mentionne **aucune** valeur sRGB ; ses 21 et 5
apparaissent au §1.4 et au point 49-3, tous deux explicitement sous « lumière par défaut
`(1, −1, 1)`, blanche, intensité 1, vue frontale » — c'est-à-dire la **conséquence pour
`REQ-SCN-048`**, dont `Backdrop.Color` vaut noir par défaut. Le 3ᵉ critère d'`AMD-049` v1.1 semble
donc avoir repris ces deux chiffres du point 49-3 en leur attachant, par erreur, la configuration
des deux premiers critères.

## 2. Pourquoi cela ne change rien au modèle

Le calcul de `REQ-SCN-075` lui-même n'est pas en cause : il est complet, et les deux premiers
critères (linéaires) le verrouillent sans ambiguïté. Seul le **troisième critère** est inexploitable
tel quel. L'enjeu est donc de vérification, pas d'implémentation : aucune des deux lectures ne
modifie une ligne de shader.

## 3. Questions posées

1. Le 3ᵉ critère de `REQ-SCN-075` doit-il lire **(26, 26, 26) hors ombre et (7, 7, 7) dans
   l'ombre** — c'est-à-dire garder « la même configuration » que les deux vecteurs linéaires, avec
   `Light.Direction = (0, 0, 1)` ?
2. Ou bien doit-il lire « **avec la lumière par défaut `(1, −1, 1)`**, albédo nul : sRGB
   (21, 21, 21) hors ombre, (5, 5, 5) dans l'ombre » — c'est-à-dire la configuration du §3 point 2
   et du point 49-3 de la relecture ?
3. Accessoirement, le critère pourrait publier **les deux**, ce qui exercerait le modèle sous deux
   directions de lumière et rendrait la dépendance en `nl`/`lh` observable ; c'est la forme la plus
   utile pour un vérificateur, et celle que la mise en œuvre couvre déjà (§4).

## 4. Choix provisoire

Le modèle est implémenté tel qu'écrit au §2 de l'amendement, sans aucune liberté prise. Les tests
du lot verrouillent **les deux** jeux de chiffres, chacun avec sa propre configuration, de sorte
qu'aucune des deux réponses possibles ne demandera de changer le code :

- `impl/tests/Acceptance/Amd049Tests.cs`,
  `REQ_SCN_075_a_zero_albedo_reads_sRGB_26_and_7_under_the_front_light` — la configuration
  littérale du 3ᵉ critère (`Light.Direction = (0, 0, 1)`) : 26 et 7 ;
- `impl/tests/Acceptance/Amd049Tests.cs`,
  `REQ_SCN_048_a_black_backdrop_reads_21_lit_and_5_shadowed` — la lumière par défaut
  `(1, −1, 1)` du §3 point 2 : 21 et 5, chiffres repris dans le critère d'acceptation de
  `REQ-SCN-048` (`impl/tests/Acceptance/SceneCaptureTests.cs`,
  `The_backdrop_appears_behind_the_scene_and_receives_the_shadows`).

Les deux tests portent la marque `// Q-083`.
