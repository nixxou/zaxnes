# Q-009 — Association ROM ↔ profil : persistée dans `rom.json` ou dans `library.json` ?

- **Ouvert par** : R3 (côté propre), lot L2, 2026-10-20
- **Documents concernés** : SPEC-03 REQ-PROF-064 (et sa note) ; SPEC-09 REQ-PERS-031,
  REQ-PERS-025, §4.4 (disposition de l'original, informative), §4.5.2 (`library.json`)
- **Classe** : C (contradiction entre deux specs)
- **Priorité** : P2 (aucun effet observable pour l'utilisateur ; effet sur le nom et le format
  du fichier écrit)

## Contradiction

- **SPEC-03 REQ-PROF-064** (P1) : « le chemin choisi est mémorisé pour ce jeu (clé = id du
  profil) **dans `rom.json`** (SPEC-09) et réutilisé aux lancements suivants ». Sa note ajoute :
  « format exact de `rom.json` (liste `Items` d'objets `{id, romPath, title, lastTime}`) :
  SPEC-09 ». Son critère d'acceptation dit « le chemin est mémorisé dans `rom.json` sous l'id
  `"1"` ».
- **SPEC-09** range `rom.json` au §4.4, « Disposition observable de l'original
  (**informatif**) », et fixe pour la réimplémentation le fichier **`library.json`**
  (§4.5.2, REQ-PERS-031, REQ-PERS-037, avec `schemaVersion` au sens de REQ-PERS-024). Mieux :
  **REQ-PERS-025** (P3) dit que la réimplémentation « N'EST PAS TENUE de lire les fichiers de
  l'original » et « PEUT proposer un import unique de `rom.json` » — ce qui n'aurait pas de sens
  si `rom.json` était aussi son fichier d'écriture.

Autrement dit, REQ-PROF-064 cite le fichier de l'original comme si c'était celui de la
reconstruction. Les deux ne peuvent pas être vrais à la fois : `rom.json` n'a pas de
`schemaVersion`, pas de jaquette, et son champ `lastTime` s'appelle `lastPlayed` dans
`library.json`.

## Choix provisoire

La **règle** de REQ-PROF-064 est appliquée telle quelle (aucune reconnaissance automatique de la
ROM, aucun hachage, clé = identifiant de profil, chemin mémorisé et réutilisé), mais le
**fichier** est celui de SPEC-09 : `library.json` (§4.5.2). L'import unique de `rom.json`
(REQ-PERS-025) est implémenté et testé, ce qui couvre le cas de l'utilisateur qui vient de
l'original.

Références dans le code : `Sen.Profiles.Library.GameLibraryStore` (`// Q-009`,
`Save`/`Load` sur `library.json`, `LoadRomPaths`/`ParseRomPaths` pour `rom.json`),
`GameLibrary.ApplyRomPaths`. Tests :
`CatalogueAndLibraryTests.REQ_PROF_064_the_rom_association_survives_a_save_and_a_reload`,
`…REQ_PERS_025_the_rom_paths_of_an_original_rom_json_can_be_imported`.

## Question posée à R0

Confirmer que `library.json` est le fichier d'écriture et que la mention de `rom.json` dans
REQ-PROF-064 décrit l'original (auquel cas corriger la phrase et son critère), ou imposer
l'écriture au format `rom.json` de l'original.

## Réponse R0 (2026-10-20, normative)
Choix provisoire validé : l'association ROM ↔ jeu est persistée dans `library.json` (SPEC-09). `rom.json` est le format de l'original, lu par un importeur optionnel.
