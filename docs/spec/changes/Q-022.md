# Q-022 — Mode 2D : les tuiles libérées par l'extraction de bande réapparaissent et doublent le texte

- **Ouvert par** : R3 (côté propre), lot L7a, 2026-10-20
- **Documents concernés** : SPEC-04 REQ-E3D-381 (mode 2D, extraction de bande) et sa note
  « Le sort, dans la frame courante, des tiles libérées par l'extraction […] n'est **pas
  spécifié** » ; SPEC-06 REQ-SCN-055 (le mode 2D montre l'image du jeu dans la scène)
- **Classe** : A (comportement explicitement non spécifié, mais visible à l'écran)
- **Priorité** : P2 (le mode 2D est l'entrée par défaut quand aucun profil ne correspond)

## Écart

REQ-E3D-381 fait croître une shape de fond inconnue par 4-voisinage « en ajoutant chaque voisine
libre, inconnue, non CHAR, de même `pal` […] **et dont l'image n'est pas déjà dans la shape** »,
puis, si la shape ne remplit pas sa boîte, en **extrait la première bande contiguë** de lignes
pleines et **libère les autres tiles**. La note conclut que le sort des tuiles libérées dans la
frame courante n'est pas spécifié.

Mesure côté propre, en harnais, sans profil (donc mode 2D), sur la ROM de test publique
`240pee` (240p Test Suite, écran de titre) :

- l'image NES de référence compte **960 cases de fond** affichées (32 × 30) ;
- la liste de tuiles à dessiner de REQ-E3D-641 en compte **1004** ;
- sur la capture 3D, les **3 à 4 premières tuiles de chaque ligne de texte sont dessinées deux
  fois**, côte à côte : « This is free » devient « ThisThis is free », « Concept by » devient
  « ConConcept by », « 240p Test Suite » devient « 240240p Test Suite ».

Le rendu dessine fidèlement ce que la liste contient (vérifié par
`MaterialTests.REQ_SCN_055_in_2d_mode_a_learned_band_keeps_its_tiles_in_order`, qui montre
qu'une bande de quatre images distinctes sort dans le bon ordre et aux bonnes positions) :
l'écart vient de la conversion, pas de SPEC-06.

Reproduction :

```
Sen.Harness render --out <dir> --rom 240pee.nes --run 400 --angles 0,0 --size 1024x768
```

La capture 3D est écrite à côté de l'image NES plate (`240pee-2d.png`), ce qui permet de
comparer les deux.

## Choix provisoire

Aucun : le rendu dessine la liste telle qu'elle lui est livrée. Le comportement observé est
celui que l'implémentation actuelle de REQ-E3D-381 produit, dans la zone que la note déclare
non spécifiée.

## Question posée à R0

Spécifier le sort des tuiles libérées par l'extraction de bande :

1. elles ne sont **pas affichées** dans la frame courante (le texte n'est alors dessiné qu'une
   fois, mais une partie de l'écran manque pendant une frame) ;
2. elles forment une **nouvelle shape** dont la boîte de placement est la leur (ce qui est
   sans doute l'intention, et n'aurait pas d'effet visible) ;
3. le comportement actuel est celui de l'original et doit être conservé.

Le point mérite une mesure en boîte noire au round 2 : l'écran de titre d'une ROM quelconque en
« 2D Mode » suffit à trancher.

## Réponse R0 (2026-10-20, normative)
Le mode 2D (entrée « 2D Mode » et ROM sans profil) affiche l'**image en pixels 256×240 produite par le cœur** (SPEC-02), plaquée sur le plan NES selon le repère de REQ-E3D-410, et non une recomposition des enregistrements de tiles **(D)**. REQ-E3D-381 ne s'applique plus au rendu du mode 2D.
