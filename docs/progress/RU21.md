**The one real architecture difference.** In .NET `ProfileTile`, `ProfilePattern` and
`PatternVariant` are mutable classes and resolution mutates them in place. In Rust the decoded
model is immutable and shared through `Arc`, and the encoder keys its reference envelopes on
`Arc::as_ptr(..).addr()` (`wire/encoder.rs:374`), so the identity graph is what makes the
rewrite of REQ-PROF-084 lossless. Safe Rust, no interior mutability: resolution **rebuilds** the
patterns it touches, one new `Arc` per distinct old `Arc`, substituted everywhere that `Arc`
appears (both root lists and the memorised slots). The identity graph stays isomorphic, so the
rewrite is unaffected, and the cost falls only on the patterns a resolution actually changed.

The engine cannot borrow the host's profile across frames, so the tile table
(`HashProfileTiles`) owns its own `Arc<ProfilePattern>` list in registration order and the
registry keeps `profile index → PatternId`; `engine.load_profile` takes the table by value.

**The textures are derived, not stored** (decided at step 4). In .NET `RebuildChangedTextures`
recomputes each variant's texture in place every time tiles are resolved, which is the whole of
the V2-34 trap. Here the variant keeps `textureKind` and field 24 exactly as read and **no**
computed texture: `hash::default_texture::PatternTextures::texture_of` derives the texture of a
(pattern, variant) pair where it is used, with the pattern's default texture built on first need.
Three things fall out: the trap cannot happen (there is no cached exclusive-or to go stale, and a
tile resolved in the frame changes the texture by itself), the rewrite of REQ-PROF-084 stays
lossless for free (it writes back field 24 as read), and the `Arc` identity graph the encoder's
reference envelopes key on is never touched. It also settles a question .NET leaves open — a
variant shared between two patterns with different grids would have two different exclusive-ors
and one mutable texture field — which measurement shows is moot in the corpus: **0** variants of
the 101 files are shared between patterns.

## The traps the .NET lot already paid for

- **V2-34** (changelog §2.2): a `textureKind = 2` texture built while the tiles are pending is
  `X XOR 0`. It MUST be rebuilt as soon as the tiles are resolved — at load from the ROM or the
  cache, and again while playing — and the pattern instance must take the **new** texture, not
  only `geo`/`fullWarp`. Without it: wrong colours, black cells, and tiles that stop being full
  (24 vertices instead of 48). This is what the « 3dh = 3dn » test catches.
- **Q-178 §1**: on a mapper-0 CHR-RAM cartridge a visible tile is always also an aligned CHR-RAM
  block, so the two resolution paths are tested separately (engine without a CHR-RAM source for
  the screen path; app with a real core for the CHR-RAM path).
- **Q-178 §3**: `Final_Fantasy_USA` leaves **66** strings pending, not 67 — the four flips of
  REQ-PROF-078 resolve one more than an unflipped scan.
- **Q-179**: the background map is built on every background instance of the frame (hidden ones
  and those whose geometry is not ready included) and on every tile of their shapes; only step 2
  is limited to drawn tiles.
- **Q-180**: `RotOverride` accepts what any `Vector3` write of the API accepts (a bound vector, a
  `Vector2` at z = 0) and raises for anything else; reading gives a `Vector3` copy.

### 2026-11-10 — step 5 done

Where the sixteen bytes of a waiting tile come from, and the cache that spares the search.

  header, the 512-byte trainer when bit 2 of byte 6 is set, the NES 2.0 sizes when

- `zax-profiles/src/hash/raw_tile.rs` — `flipped_planes`, the four mirrorings of REQ-PROF-079

  `reverse_bits().swap_bytes()`, both is `reverse_bits()`. That is what makes the scan cheap,
  since the prefix of REQ-PROF-077 is a function of the planes: a window whose prefix no waiting
  string carries costs four multiplications and no digest at all, and the sixteen bytes are
  rebuilt only for a window the prefix let through. A test confronts it with `flipped` over
  sixteen vectors and the four flips.
- `zax-profiles/src/hash/tiles.rs` — `TileResolver`: which manifest strings have their bytes, the
  prefix filter as a count per prefix (a legacy digest has no prefix and is hashed in full, which
  the 101 files never need), `offer` for one window and its four mirrorings, `resolve_from_rom`
  for the PRG zone then the CHR zone at every byte position with an early stop, and `apply_cache`.
  `apply` rebuilds what a resolution changed: one new `Arc` per distinct old one, substituted in
  both root lists, and the memorised slots — which hold their patterns by value, outside the
  shared graph — rebuilt in place. A resolution that resolves nothing rebuilds nothing, which a
  test checks on the `Arc` addresses themselves.
- `zax-profiles/src/hash/tile_cache.rs` — the cache of REQ-PROF-082: a header line then one
  `<string> <32 hex digits>` per pair. Every entry is verifiable — the string recomputes from the
  bytes, as an identifier or as a legacy digest — and an entry that does not recompute, a file
  without the header, a truncated file and bytes that are not UTF-8 all give nothing. The file is

### 2026-11-10 — step 7 done

REQ-CORE-123, the core's CHR-RAM read, which step 8's in-game resolution needs.

The buffer was already there and already shared by every board that writes CHR
(`CartridgeMemory::chr_ram`, used by nine mappers): what the requirement asks for is that the
**core** offer it, read only, between two frames, addressed linearly from 0 in cartridge order
whatever banks the PPU sees. So `Cartridge::chr_ram` borrows it and `NesCore::chr_ram` answers
`&[]` when no ROM is loaded — the length being the size the requirement wants, zero for a
CHR-ROM cartridge. Nothing is latched, no bank moves, no cycle is spent, so the "no side effect
on the emulation or its determinism" clause holds by construction rather than by care.

header byte 5 at 0, so 32 KiB of CHR-RAM and no banks. A 90-byte 6502 program waits two vblanks

— the one it just wrote — and turns rendering on. So the frames the core produces are **drawn
from** the CHR-RAM the test reads, which is what makes the determinism case worth asserting:

- size 32 768 and the sixteen bytes at `0x130` to `0x13F`, the rest of the memory still zero, and
  a background record of the frame carrying exactly those planes;

- twelve frames, one run reading the CHR-RAM every frame and one never: the same frame batches
  every frame, the same savestate at the end, the same CHR-RAM. The read is folded into a digest

### 2026-11-10 — step 8 done

The resolution while playing, in the engine: where a waiting cell goes, what a resolution rebuilds,
and when it costs nothing.

**A waiting cell interns no image at all.** That is the one decision the rest follows from. The
engine's unit of identity is `TileImageKey` (two planes, two flips), and a waiting tile has no
planes: giving it an image would mean widening that key on the hot path of every profile, 3dn
included. An absent cell already means everything REQ-PROF-081 asks for, and means it in the
existing code: it is equal to no tile of the screen (so it cannot recognise anything), it is in no
`Img(P)` and in no adjacency pair (so the region cannot grow into it, and the pattern draws with
its resolved cells alone), it has no voxel field and therefore no mesh, and `ObjectTexture` already
reads an absent cell as colour 0, which is REQ-PROF-081's "leaves its 8 × 8 pixels at 0" and
REQ-PROF-083's "a waiting cell gives 0 pixels". So the four clauses of REQ-PROF-081 cost one
`filter` in the cell interning. The same choice as .NET's `InternCells`, reached from the other
end.

- `zax-profiles/src/hash/tiles.rs` — `has_waiting_tile`, `waiting_keys_of` and `resolved_grid`
  (the grid of a pattern with every fillable waiting tile turned into an ordinary one, or none
  when nothing changes). `substitute_in_place` is now a two-line caller of the third, and
  `PatternTextures::has_waiting_tile` of the first.
- `zax-engine3d/src/hash_tiles.rs` (new) — `HashProfileTiles`: the resolver, the profile's
  patterns in registration order with their `PatternId`, and the index that makes a resolution
  cost only what it changes — the distinct strings a cell named while waiting (in pattern then
  cell order, never a hash order), the patterns holding each, and which are still waiting.
  `offer_frame_tiles` and `offer_chr_ram` confront the two sources of REQ-PROF-080 with the
  manifest; `rebuild_changed` moves the strings that have their bytes out of the waiting set and
  rebuilds the patterns that held them, one new `Arc` each.

  cells skipped), `reload` and `reload_from_profile`, and `has_placeholders`, which step 11 will

  take the table by value; an added entry point leaves the forty-odd callers of `load_profile`
  alone and says the same thing), `hash_tiles`, `offer_chr_ram`, and the resolution at the head of
  `convert`.

**Where each source enters.** The frame's tiles are in the batch `convert` already receives, so
that half can never be forgotten: `convert` resolves from `batch.records` before intake and
segmentation, and a tile resolved there is recognised in that very frame. The CHR-RAM cannot
travel that way — the app captures the records into its own buffer and converts later, while the
CHR-RAM is in the core, and a `&dyn ChrRamSource` held across frames (what .NET does with GC
references) would borrow the core for the life of the engine. So the host offers it explicitly:
`engine.offer_chr_ram(core.chr_ram())` right before `convert`, which borrows it for the call only.
Step 9 wires that into `GameSession`.

**Three deviations from .NET, all in the Rust direction:**

1. *The textures are derived* (step 4), so `RebuildTextures` has no equivalent and the V2-34 trap
   has no place to hide — except in the instance, which caches the derived texture in
   `PatternInstance::texture`. `apply_variant_geometry` recomputes it, and the regression test
   fails without that line (texel 3 where 2 is expected), exactly as the .NET lot measured.
2. *The cost index.* .NET walks `TakeChangedPatterns`; here a resolution looks up only the
   patterns that named a string that has just been resolved. A frame that resolves nothing costs
   one `Option` test and one `is_empty`.
3. *The unchanged CHR-RAM block is skipped*, which REQ-PROF-080 allows "à condition que l'ensemble
   résolu à chaque frame soit celui du parcours complet". It is: the waiting set only ever shrinks,
   so a block already confronted resolves nothing new. A test puts the stepwise walk and the full
   walk side by side and compares the resolved sets entry by entry. Mega Man 2 keeps 144 strings
   waiting for the whole session (Q-178 §2), so this is the difference between 8 192 prefix
   computations a frame and a 32 KiB comparison.

**One hazard .NET leaves open, closed here.** An in-game resolution interns an image *after*
`profile_image_count` was fixed at load, so the registry counts it among the images met while
playing — and `state_codec::read` drops those and re-interns only what the state recorded. The
resolved cell would have kept a `TileImage` whose identity no longer exists: its candidate list
would be another image's. Bumping `profile_image_count` is not the answer either, since the codec
refuses a state whose count differs, so a savestate taken before a resolution would stop loading.
So the table keeps every pattern a resolution has rebuilt, and `read` takes them again at the end:
the images come back, with identities interned after the restored ones, and REQ-PROF-080's "a
resolved tile never goes back to waiting, a state load included" holds. A test asserts it, frame
and all: after the round trip the pattern is still recognised whole.

  the camera. Writing accepts nil and what any `Vector3` write of the API accepts (a bound vector,
  a `Vector2` at z = 0) and raises for anything else (Q-180).
  `SceneCamera` gains `rot_override`, applied at the head of `advance` **before** the wrap of

### 2026-11-10 — step 12 done

The measurements, and the three cost regressions they found. **None of them was visible in a
test**: every suite was green at step 11, and the owner's rule — "a 3dn profile and a picture
without transparent objects must cost nothing more" — is exactly what a green suite cannot say.

**The instrument.** `rust/tools/perf/`, as lots PR-1 and the MF line left it: every compared
commit extracted by `git archive` into a brand-new directory with its own `CARGO_TARGET_DIR`
(`build-clean.sh`), callgrind in the WSL2 Ubuntu, instruction counts (`Ir`) which are
deterministic to the instruction. Two sets: `callgrind-set.sh`, the thirteen PR-1 ROMs, 300
frames, **no profile** — the core and the conversion of a picture with no 3D pack at all; and
`callgrind-l2.sh`, the five level-2 games with their **3dn** packs, 600 frames after 120 of
warm-up, inputs pressed (`ZAX_L2_ROMS=…/test-originals`,
`ZAX_L2_PACKS=…/campaign/play-user/profiles`). Base `591836cc`, against the tip of this lot.

#### What the first run said, and the three faults behind it

| | PR-1 total | worst PR-1 ROM | level-2 total | worst level-2 game |
|---|---|---|---|---|
| step 11 as committed | +0.080 % | duelito **+0.263 %** | +0.248 % | mm2 **+0.427 %** |
| after the three fixes | **+0.025 %** | smb3 +0.051 % | **+0.028 %** | metroid +0.042 % |

1. **A branch that may call costs the loop that never takes it.** `add_instance` tested
   `removable` *inside* the tile loop, so every drawn tile of every picture — 3dn, no profile,
   nothing transparent — paid the spills and reloads the possible `removed_sides` call needs
   around it. On duelito that was **+19.0 M instructions**, 95 % of the whole regression, about
   26 instructions per drawn tile for what reads as one bool test. The fix: the decision is per
   **instance**, so it now picks between two monomorphisations, `push_tiles::<false>` and
   `push_tiles::<true>`. With `REMOVAL = false` the removal is dead code and the mesh comes from
   `mesh_of`, so the loop is instruction for instruction the one before the amendment. duelito
   went from +0.263 % to +0.045 %.
2. **The full-tile scan ran at load, for every profile.** `is_full_tile` walks the `8 × 8 × D`
   voxels of a field, three slots each, and step 10 ran it over every mesh of every 3D object
   while building it. Mega Man 2's 3dn pack — no transparency in it at all — paid **+73.4 M** in
   `GeometryBuilder::build` for an answer nothing would ever ask for. The scan moved to
   `TileVoxels::is_full` and is now taken **on demand** and memoised per mesh
   (`ObjectGeometry::full_tiles`, empty until the first question). mm2 went from +0.427 % to
   +0.039 %, smb3 from +0.302 % to +0.025 %.
3. **The mesh lookup took `&mut self`.** `mesh_of_without` needed it only to memoise the fifteen
   variants, and the draw list calls it once per drawn tile. The variants moved behind a
   `RefCell`, so the trait method takes `&self` again and the cell is borrowed only on the removal
   path, after the two tests that send an ordinary tile straight back. The same change made the
   variant storage lazy: an object no transparent instance ever covers now reserves **nothing**
   instead of sixteen slots per mesh.

**One fix that was measured and rejected.** Building the background map on demand, from the first
drawn instance that could lose a face, makes an opaque picture free of even the gate walk — and
seven of the thirteen ROMs did go to or below the base. But it puts a call to a `&mut self` method
in the drawing loop, and the whole tile loop de-inlined around it: `push_tiles`,
`InstanceLook::tile`, the `Mat4` product and a `memcpy` all left `build`, and duelito went to
**+0.149 %**. `#[cold]` and `#[inline(never)]` did not help (+0.149 %), which is what says the cost
is the de-inlining and not the spills. So the map is built before the loop, the gate's cheap
predicate (`is_transparent`, two field reads) is tested before the shape is even looked up, and
the comment in `map_background_cells` records the figure so the next reader does not retry it.

#### The « 3dh = 3dn » regression (owed by step 9), and what it found

`zax-engine3d/tests/engine3d/amd062_hash_equals_3dn_tests.rs`, 3 cases on the five games of the
changelog with their real packs and ROMs (`ZAXNES_PROFILES` + `ZAXNES_ROMS`, `#[ignore]`d). It
loads the 1.x pack and the 2.1 pack, resolves the second from the game's own ROM, and compares.

- **REQ-PROF-075 to 079, the whole chain in one figure**: every cell the ROM resolved carries
  **exactly** the planes and the mirroring of its 1.x homologue — **53 173 cells over the five
  games, 0 differing**. One wrong bit in the identifier, the mixing prefix, a mirroring or an iNES
  zone would move a cell.
- **The V2-34 regression**: for every 3D object whose pattern is fully resolved, the mesh and the
  texture are the homologue's — 0 tile different, 0 texture different, over 30 087 tile meshes.
- **REQ-PROF-078 on the real corpus**, measured and pinned to the string: SMB3 4 856/4 856,
  Legend Of Zelda 1 035/1 035, Super Mario Bros 481/481, **Contra 1 603 of 4 574** (mapper 2,
  UNROM, no CHR zone at all: the game writes its own pattern tables, which is the whole reason
  REQ-PROF-080 point 1 exists) and **Mega Man 2 5 353 of 5 497, 144 waiting** — Q-178 §2's figure,
  reached here from the other end and now asserted.

**Two findings worth the owner's eye.** First, the 2.1 packs are **not** re-encodings of the 1.x
packs: the owner re-authored a few variants between the releases. Super Mario Bros's pattern 135
declares `fullWarp` in 1.x and not in 2.1, which moves a mesh from 108 triangles to 64 — 4
patterns of that pack, 11 tile meshes. The probe that found it compared the two documents at the
profile level and showed **0 grid and 0 plane differences** against **4 variant differences**, so
it is artwork and not decoding. The test therefore steps over a pattern whose authored variants
disagree, counts them, and prints them, so a *new* difference is noticed rather than absorbed.
Second, `bench-core` and `meshes` have no 3dh wiring — step 9 gave `--rom` to `render` only — which
is why this regression is a Rust test and not a `--dump-meshes` diff; the test is the stronger
form anyway, since it compares planes and whole meshes rather than a dump.
