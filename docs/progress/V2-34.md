# V2-34 — A « 3dh » profile renders exactly like its 3dn counterpart (AMD-062)

Defect found by the R5 pass. Requirement: AMD-062 v1.2 §1, REQ-PROF-078, REQ-PROF-079,
REQ-PROF-081, REQ-PROF-083 — once its tiles are resolved, an appariable « 3dh » profile has the
same content as its 3dn counterpart, so the conversion and the drawn meshes must be **identical**
for the same ROM and the same inputs.

## Root cause

**Two defects, both of them a texture of REQ-PROF-083 left as it was built while the tiles were
still pending.** Neither is in the resolution itself: the identifiers, the four mirrorings of
REQ-PROF-079, the bytes a resolved tile receives and the pending rules of REQ-PROF-081 all check
out. What was wrong is what happens to a `textureKind = 2` texture *after* a resolution — that
texture is the exclusive or of the stored field 24 with the pattern's **default texture**
(REQ-PROF-083), so it is only correct once the tiles it is built from are known.

1. **At load time (`HashProfileTiles.PrepareForRom`).** The decoder builds the variant textures
   at the end of `ProfileWireCodec.DecodeHashProfile`, when **every** tile is still pending: the
   default texture `B` is then all zeros, so `X XOR B = X` — the variant kept the stored
   exclusive-or payload itself instead of the texture — and a variant whose shape differs from
   `B` kept the fallback of REQ-PROF-083. The cache and the ROM resolve the tiles right
   afterwards, and nothing rebuilt those textures: both hosts
   (`EmulationHost.PrepareHashTiles`, `RenderExport`) go straight from `PrepareForRom` to
   building the patterns, and the engine's own rebuild (`ConversionEngine.ResolvePendingTiles`)
   only runs on a resolution made while the game runs. Fixed by rebuilding the textures of the
   patterns the resolution changed at the end of `PrepareForRom` — the only place that can, since
   no engine exists yet. This accounts for the four rows whose tiles come from the ROM file.
2. **While the game runs (`PatternInstance.ApplyGeometry`).** A resolution rebuilds
   `variant.Texture` as a **new object**, but `PatternInstance.Texture` was a copy taken once in
   `FromVariant`, and `ApplyGeometry` — what `EnginePattern.ReloadFromProfile` calls after a
   tile is resolved — only put back `Geometry` and `FullWarp`. The instance therefore went on
   drawing the texture computed while the cell was pending, even though its geometry and its
   images were right again. Fixed by putting the variant's texture back there too; a script never
   writes `Texture` (it redirects `TextureSource`, SPEC-05 REQ-LUA-097), so nothing a script set
   is touched. This is the whole of Contra, a CHR-RAM board whose patterns resolve in play.

The visible symptom follows from either one: a wrong texture has pixels of colour 0 where the
real one has none, the tile stops being full, and SPEC-04B/AMD-063 keeps the inner faces it
would have removed — hence 24 vertices in 3dn against 48 or 80 in « 3dh », and the wrong colours
on the trees and the black squares of the Super Mario Bros. 3 map.

- Fixes: `HashProfileTiles.PrepareForRom` + new `RebuildChangedTextures()`;
  `PatternInstance.ApplyGeometry` + new `TextureOf(variant)` helper shared with `FromVariant`.
- Unit regression for the second one, which the five rows reach only through a real dump:
  `Amd062TileResolutionTests.A_resolution_while_the_game_runs_gives_the_instance_its_rebuilt_texture`
  — a `textureKind = 2` variant on a 2 × 1 pattern, resolved in the frame being converted, has to
  end up with the texture an already resolved load gives. Checked to fail without the fix.
- No Q ticket: the spec is not ambiguous here. REQ-PROF-083 says the texture is rebuilt « once
  the tiles of the pattern are resolved », and REQ-PROF-080 says « the patterns, variants and
  textures that contain it are recomputed before this frame is rendered ». Both were simply not
  carried out on those two paths.
