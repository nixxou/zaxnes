# V2-34 — A « 3dh » profile renders exactly like its 3dn counterpart (AMD-062)

Defect found by the R5 pass. Requirement: AMD-062 v1.2 §1, REQ-PROF-078, REQ-PROF-079,
REQ-PROF-081, REQ-PROF-083 — once its tiles are resolved, an appariable « 3dh » profile has the
same content as its 3dn counterpart, so the conversion and the drawn meshes must be **identical**
for the same ROM and the same inputs.

## Notes

- Session start: branch `dotnetupdated`, tree clean at `d374cd27`.
- Step 1, two new test files in `tests/Zax.Harness.Tests/`:
  - `Amd062ProfileParityTests.cs` — the five rows of the R5 pass, each skipped when its dump is
    absent (`ZAXNES_ROMS`, no machine path committed). Both captures go through the harness's own
    `render --rom` path with an **empty** tile cache, and what they drew is compared twice over:
    tile by tile, with a per-tile report naming how many differ, and then as the two
    `--dump-meshes` exports, character for character (`MeshDump.Write`, Q-081).
  - `Amd062SyntheticParityTests.cs` — the same equality without any dump: the « 3dh » profile is
    resolved from the synthetic iNES file of REQ-PROF-078, every tile placed **mirrored
    horizontally** so that REQ-PROF-079 does the finding, and both profiles then convert the same
    synthetic frame (the grids of the profile's own patterns laid out on the background, the ones
    carrying a `textureKind = 2` variant first).
  - The « capture pixels » of the rows are read without a GL context: a drawn tile's signature
    carries an FNV-1a 64 of every texel of its `ObjectTexture`, plus its material, alpha, palette
    table and texture mapping. A GPU campaign is out of the question on this machine, and a
    differing pixel cannot hide from the texels it comes from.
  - Both files take the **host** path — `PrepareForRom` then `LoadProfile` — and resolve or
    rebuild nothing by hand. That is the point: the defect is on that path.
