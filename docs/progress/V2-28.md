## Notes

### Root cause (step 1, confirmed by test)

`tools/Zax.Harness/RenderExport.cs:969` runs `runtime.InvokeEnd()` — the **end-of-game** hook of
REQ-LUA-021 — *before* the captured scene is finished (`scene.Camera.SnapToSetpoints()`,
`scene.GameRunning = true`, `scene.DrawList = …` at lines 984-991) and before the caller renders
the returned `SyntheticScene`. The settings→scene bridge is still connected at that moment, so
whatever an `End` hook writes on a scene-owned setting reaches the frame the capture shows.

The capture is a frame of a **running** game (`scene.GameRunning = true`); in the application
nothing is ever rendered after `GameSession.End()`, so an `End` write must not be visible.

This is exactly what both reported profiles do:

- Mega Man 2, script `stage`:
  `Start` → `oldColor, oldDir = Light.Color, Light.Direction` (the profile's stored green
  FF33CC00 / (−3,−3,1)), `Update` → white + (1,−1,1) every frame, `End` →
  `Light.Color, Light.Direction = oldColor, oldDir`. The `End` hook therefore puts the **stored
  green** back over the white the 601 `Update` calls had written. Every variant R5 tried (red else
  branch, red green-branch, `stage == 9`) renders the same green because none of them changes what
  `End` restores — which is the stored light.
- Castlevania `(U) (PRG 1)`, script `ui`: `Start` → `Color(0.8,0.8,0.8)`, `End` → `Color(1,1,1)`.
  `End` puts white back over the grey, which is the brighter HUD R5 measured (223 vs 190). **Same
  defect, not a second one.**

### The fix (step 2)

`RenderExport.FromRom` now settles the frame the capture shows **first** (the eleven `scene.*`
assignments and `SnapToSetpoints`), then seals the scene and only then runs the `End` hooks and the
report. The console output keeps its order.

`ScriptBridge.Seal(runtime)` closes the three ways a script reaches the scene:

- `Settings.Changed = null` and `Settings.ViewReset = null` — every scene-owned setting of
  SPEC-09 §4.1 at once (light, field of view, smoothing, shadows, skybox, background, clip
  margins, visual style), not only the light;
- a shared `CaptureSeal` the `HarnessCamera` and `HarnessBackdrop` views check in their setters —
  those two write straight into `scene.Camera` / `scene.Backdrop` without passing through the
  model, so the settings bridge alone would not have covered them.

The getters stay live, so an `End` hook still reads what the frame shows and cannot fail on a nil.

### The application path (step 3) — already sound, now covered

`GameSession.Create` has the right order and needed **no change**:
`SceneSettingBridge.Connect` (line 210) runs before the chunks, `model.ApplyProfile` after them
(REQ-LUA-015 step 2), `ApplyProfileScene` does `scene.Light.Reset()` then
`SceneSettingBridge.Push`, and `Start` follows. `InvokeEnd` is only reached from
`GameSession.End()` — game stopped, savestate restore, relaunch — and the next game's scene starts
from `LightState.Reset`, so no displayed frame is ever lit by an `End` write.

`tests/Zax.App.Tests/ScriptLightTests.cs`, 5 tests, all green **without touching the application**
— which is the finding: the defect was in the harness render path only, not in
`SceneScriptBridge`, not in the settings layers, not in the `Light` binding.

- `A_light_written_in_start_reaches_the_scene_over_the_stored_one`
- `A_light_written_by_an_update_hook_reaches_the_next_rendered_frame` (whole MM2 `stage` shape:
  the stored green holds until the first `Update`, then white, and it keeps holding)
- `An_update_hook_can_change_the_light_from_one_frame_to_the_next` (`$2A` written through
