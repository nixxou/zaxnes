Round 2 (same benchmark, medians of 3): `Update` 25.3 -> 25.1 us (no change: what is left per access is the cost of the mlua callback, about 1000 instructions, and a host read adds a second one), `BuildPattern` 1.47 -> 1.35 us (0.86 -> 0.82 us of setup), empty `UpdateS` 1.52 -> 0.98 us, `UpdateS` with 7 accesses 3.4 -> 2.3 us, a frame 270 -> 203 us (1.3x on top of round 1). What did it: `shape2D` stays published eagerly (a lazy one needed a protected metatable on the globals, which scripts can see, so it was reverted: C# puts none on `_G`), frame handles are keyed by integers (a slot of group and member) and retired into per-epoch weak tables keyed by integers instead of 16-byte strings (the retirement was 18 % of a frame), the budget clock starts at the first look of the count hook instead of at each hook call, the member lookup is by bytes (no UTF-8 check), the epochs are read from the object cache (no borrow of the runtime data per frame-instance access), the `UpdateS` function and `self` are fetched once per script, and the incremental collector waits for the heap to grow fourfold. Tried and dropped, no gain: typed answers instead of boxed ones for host reads (~0 ns, the cost is the Lua round trip), a cache of setting reads (the model read is cheap), the generational collector, the instruction-count hook itself costs only 5 %.

### Rust-only changes (owner requests)

Deliberate departures from the C# 0.2.0 behaviour.

- Default UI language from the OS: amends AMD-035 ("English by default" becomes "OS language if French, else English"). It applies only while no `ui.language` is saved; the choice is persisted as before (the file format is unchanged, but a `ui.language` the user holds is now written even when it equals the default `en`, so it keeps winning over the OS). The decision is `UiLanguage::from_locale`; the OS locale (`sys-locale`) is injected through `AppOptions::system_locale` and reaches the model as an environment default.
- Native file dialog (`rfd`, feature `native-dialog`, on by default): ROM, profile, cover and 3dSen-folder choices use Windows Explorer or the XDG portal (`xdg-portal` backend, no GTK, no async runtime; pure Rust plus a dlopen of libdbus), with the `ImGui` browser as the fallback (`ZAXNES_NATIVE_DIALOG=0`, no desktop session or bus, a dialog that closes with no answer within 400 ms, aarch64 Linux by default; `=1` forces it). The dialog runs on its own thread and the frame loop polls it (`FilePicker` trait, faked in `tests/native_dialog_tests.rs`); on Windows the window leaves full screen while it is open. The aarch64 build keeps the feature on (it cross-checks; the Linux dependencies are all dlopen-ed).
- Shortcut keys stay out of the game: a key press consumed by a modifier shortcut (Alt+Enter, Ctrl+O...) is hidden from the actions and the commands of the keyboard bindings until the key is released and pressed again (C# 0.2.0 also sent Enter to the game as Start on Alt+Enter). `ZaxUi::consumed_keys`, `DesktopInputSource::consume_keys`; `tests/shortcut_consumption_tests.rs`.
- Ctrl+, toggles the options window (C# 0.2.0 only opened it).
- Keyboard in the handheld mode (`--handheld`): `ui/handheld/keyboard.rs` feeds the pad of the handheld interface: arrows (and the configured direction keys) = D-pad, Enter/Space = A, Escape/Backspace = B, X and Y keys = X and Y, Tab/F1 = Menu, the configured Select and Start keys = Select and Start (so the exit combo works). The gamepad is unchanged.
- Standalone Windows exe and smaller binaries: `+crt-static` for `x86_64-pc-windows-msvc` (`.cargo/config.toml`; not verifiable on Linux, see LOCAL-CHECKS 8) and `[profile.release]` with `lto = "fat"`, `codegen-units = 1`, `strip = true` (panics still unwind; the test-profile opt-levels are unchanged). Linux release `zaxnes`: 7.66 MB before, 4.97 MB after (build 14 s to 53 s); the core goldens were re-run in release after the change.
- Handheld UI mode (new design, not a port; research in `docs/HANDHELD-RESEARCH.md` 5.3 and 5.4). Selected by `--handheld`, `ZAXNES_HANDHELD=1` (`0` forbids the automatic choice) or automatically on aarch64 Linux with neither `DISPLAY` nor `WAYLAND_DISPLAY` (`handheld_mode.rs`). It replaces the menu bar and the windows with full-screen list screens driven by the gamepad alone (no mouse, no keyboard shortcuts): ROM list from `<userdata>/roms` or `--roms <dir>` (`.nes`, sorted, L/R jump to the previous or next letter, each row shows the 3D profile that matches by remembered pair, library entry or name, else "2D"; A plays, X chooses the profile among the matching ones plus the two generic entries, Y opens the options), the in-game menu (Menu button, or a tap of Select+Start when the existing setting "Menu = Select + Start" is on: Resume, Save/Load state with slot +/-, Rewind, Fast forward, Camera preset, Options, Quit to ROM list, Exit to launcher), reduced options (language, volume in 10 % steps, render scale, shadows, frame cap 60/30, FPS counter, camera preset, gamepad bindings of player one through the existing capture), and Select+Start held 1 s to quit anywhere. Fonts, rows (at least 36 px) and padding derive from the display height (22 px at 480; 640x480, 720x480 and 720x720 checked), the control hints are the last line, and the texts are in both tables (`handheld.*` keys). Everything is a model that answers a press with a command enum (`ui/handheld/`: `rom_list`, `profile_list`, `overlay`, `options`, `exit_combo`, `pad`, `layout`), `HandheldUi` carries the commands out on the host and `draw.rs` only paints; `SdlPlatform::for_handheld` feeds the SDL game-controller events to `ImGui` (`NavEnableGamepad`, `HasGamepad`, `Gamepad*` keys) and to the pad state. `--ui-shots <dir> --handheld --size 640x480` photographs the five handheld screens. `--help` prints the new options in a separate "Rust-only options" block after the C# text, which the byte-for-byte test still compares unchanged.
- Handheld render defaults (`ui/handheld/defaults.rs`), applied as environment defaults only in handheld mode (a saved value wins): render method "Render Tex" with the scale 2/3, shadows off, anti-alias off, swap every refresh (60 fps on a 60 Hz screen). Gaps against the research notes, not invented: the catalogue has no 0.75 scale (2/3 is the nearest step), the shadow map size (the renderer supports it) and post-processing are not settings, so the options offer shadows on/off only and there is no post chain to turn off, and the frame rate setting has no 30 (the cap is the vsync interval: 60 every refresh, 30 every other). The "Rewind" row is the existing one-step rollback, there being no rewind toggle in the host.
- Shader program binary cache (`zax-render` `gl/program_cache.rs`, `Gl::cached_program`, `SceneRenderer::with_program_cache`): when the context has `glGetProgramBinary` (OpenGL ES 3.0, OpenGL 4.1, or `GL_ARB_get_program_binary`), each linked program is saved in `<userdata>/shader-cache/<hash>.bin`, the hash covering the GL renderer and version strings, the program name and both assembled sources. The next start loads the binary instead of compiling; a missing, damaged (checksum), truncated or driver-refused binary is dropped and the sources are compiled, and an unwritable folder only means no cache. Desktop runs use it too. Stale files of an older driver or shader are never read again but are not removed.
- Frame profiler and handheld diagnostics (owner request after the RG40XXV run): `ZAXNES_PROFILE=1` times each stage of a displayed frame without allocating (`frame_profiler.rs`: input, core, tile-record capture, conversion, Lua hooks, rollback snapshot, rest of the host tick, scene, UI, audio, swap, frame-cap sleep, other; the engine times its frame hooks when asked, `ConversionEngine::set_hook_timing`) and every 2 s logs mean/max per stage, the display rate and the emulated frames per displayed frame (the frame clock's catch-up, up to 5, REQ-LOOP-012); with "Show the FPS" on, a short line is drawn under the counter. At start it logs the CPU count, the cpufreq governor and frequencies, the build profile, `target-cpu` (build script), the render settings and the pacing. The log also goes to `<user data>/logs/zaxnes.log` (`app_log.rs`, line-buffered; falls back to `logs/` next to the binary, then the temporary folder, and says where), with the SDL GL context actually created, the GL strings and a WARNING for a software renderer (llvmpipe, softpipe, swrast). A handheld `--userdata` folder that refuses writes falls back to the per-user one. Not hidden in the options: the variable is enough. Also: `HostWindow::swap`/`pace` apart; in 2D mode the draw list is not built (the renderer shows only the picture); the rollback history recycles its oldest buffer (`RollbackHistory::capture_with`, `NesCore::save_state_to`, same bytes); the FPS text is formatted only when it changes. `zax-harness bench-core <rom>` gives the same stages headless. PortMaster: `Zaxnes.sh` finds the port folder from its own location, writes `log.txt` by plain redirection with a first launcher line, sets the `performance` governor for the run (restored after), passes `ZAXNES_PROFILE=1` for now, and no longer starts gptokeyb, whose Select+Start kill switch killed the process before the settings and saves were written (the program's own exit is Select+Start held 1 s); the aarch64 build uses `-C target-cpu=cortex-a53` (golden-core under qemu-aarch64 identical to the x86_64 goldens, 290 ROMs at frames 1 and 60). Two latent panics of the `sdl2` wrapper fixed on the way (`zax-platform` calls SDL directly, `unsafe` with SAFETY): `SwapInterval::from(2)` panicked when `video.vsync` 2 asked for every other refresh, and the GL attribute getters panic when the driver refuses a query (Mesa refuses the stencil size).
- Catch-up limit (owner request, handheld pacing): `CatchUp` in `emulation/frame_pacer.rs`, `FramePacer::max_backlog`, applied each tick by the host from the effective and displayed rates. Default none on a handheld (a late frame slows the game instead of piling up to five emulated frames per displayed frame), REQ-LOOP-012 elsewhere; `--catch-up <0-5>` and `ZAXNES_CATCH_UP` override it. `tests/catch_up_tests.rs`.
- Rust perf (core): PPU fast span for dots 2-255 of rendering visible lines (`Ppu2C02::run_visible_span`, `Mapper::chr_view` / `ChrView`), bit-identical (goldens); FF1 x86 core 1.18 -> 0.87 ms/frame.
- Rust perf (render): uniform value cache in `ShaderProgram` (identical uploads skipped, FNV name hash) and texture / vertex-array binding cache in the scene passes, pixel-identical (Zelda II and the 36 campaign captures at tolerance 0).
- Rust perf (render): instanced draws through the `ZaxInstances` uniform block (consecutive same-state tiles, pixel-identical), and the "grouped opaque draws" setting (`set_group_opaque_draws`, handheld default, `ZAXNES_GROUP_DRAWS`, harness `--group-draws`): Zelda II world map 1559 -> 72 GL draws, a few edge pixels may change.
- No rewind on a handheld (owner request): `EmulationHost::rollback_enabled` false with `--handheld` (no savestate every 60 frames), and the in-game menu loses its "Rewind" row (`handheld.menu.rewind` removed).
- Rust perf (app): "emulation on a separate core" (`core_worker.rs`, `GameSession::prepare_frame_timed` / `launch_prepared` / `complete_frame_timed`, `EmulationHost::separate_core`, handheld default, `ZAXNES_SEPARATE_CORE`): each frame runs on its own thread while the previous one is drawn, same emulation and script order, one frame of extra display latency. `tests/separate_core_tests.rs`.
- Rust perf (engine, render): `FastMap` / `FastSet` (Fx hasher, `zax_engine3d::hashing`) for the per-frame maps of the engine and the renderer caches, output identical; Zelda II draw list build -42 % on x86.
- Frame profiler: the scene stage is split into "list" (the engine's draw list), "collect" (the renderer's tile collection, `RenderStatistics::collect_time`) and "scene" (the renderer's passes).
- Region from the ROM by default (owner request, desktop and handheld): `emu.auto_tv_mode` is an environment default `true` (a saved value wins; C# 0.2.0 defaults to off), so a ROM whose header says PAL runs at 50 Hz. The handheld options get a "Region" row (Auto (ROM) / NTSC / PAL; Auto applies at the next game start, NTSC and PAL at once).
- Handheld: catch-up 2 by default (core on its own thread), generational Lua collector setting (handheld default, `ZAXNES_LUA_GC`): the multi-ten-millisecond collection stalls are gone (x86 max 62.8 -> 2.7 ms).
- Rust-only settings (owner request): `emu.catch_up` (None, 1-5 frames; 5 = REQ-LOOP-012 by default, None on a handheld; `--catch-up` / `ZAXNES_CATCH_UP` still force it) and `emu.lua_smooth_gc` (on by default, desktop and handheld; `ProfileScriptRuntime::set_smooth_gc`, applied at once; first tried as a generational collector, whose majors stalled 120 ms). Both appear in the Emulation tab of the options window (no Lua name, `lua-api` dump unchanged); the handheld options get a "Catch-up" row. Catch-up 2 on the device made heavy scenes worse (the second frame of a displayed frame waits for the emulation thread in series), hence None there.
- Rust perf (app): emulation ahead (`GameSession::capture_in_flight` / `launch_ahead` / `finish_captured`, `EmulationHost::core_ahead`): with the separate core, a profile whose scripts never name a core-facing member (`CORE_MEMBERS`) runs frame N+1 while frame N is converted and its hooks run; same frames (tests), same latency.
- Lua collector: the smooth incremental tuning replaces the generational mode (`emu.lua_smooth_gc`), worst hook frame on Zelda II x86 136 -> 2.5 ms; handheld catch-up back to the default 5.
- Rust perf (core): the PPU fast span also covers boards that watch the PPU bus or latch on fetches (MMC3, MMC2/MMC4, Rambo1, MMC5): `run_visible_span_through_bus` keeps the per-dot work in one loop but fetches through the full bus path, so the board sees the same addresses at the same PPU clock; goldens identical. SMB3 (MMC3) x86 core 1.36 -> 1.24 ms/frame.
- Rust perf (core): the APU mixes its level only when something it depends on may have changed (a channel timer that moved its sequencer, shift register or DMC bit, a frame-counter step, a register write, a reset, a loaded state, a region change) instead of every CPU cycle; goldens (audio included) identical. SMB3 x86 core 1.24 -> 1.13 ms/frame.
- Emulation ahead with `ReadMem`: the console RAM is copied when the frame comes back (`MemorySnapshot`) and the scripts' `ReadMem` reads it while the core runs the next frame (the bytes a serial read would see); a read of cartridge space turns emulation ahead off for the session (logged). 95 of the 101 3dSen profiles can now run ahead (all 25 `ReadMem` calls of the 9 profiles using it address console RAM); the 6 others use the input hook or the Zapper/port API. Test: a script reading memory sees the same bytes ahead.
- Grouped draws also reorder the tiles inside each transparent object by draw state (depth-only pass then equal-depth colour pass, so the order inside an object only matters on exact ties; the HUD, one plane, is left alone). Blaster Master 330 -> 206 GL draws; the 36 grouped campaign captures are identical to the previous grouped ones.
- Rust perf (engine): the draw list computes `Pos . R . S` once per instance and multiplies it by each tile's translation, in the same order as the full product (identical floats); draw list instructions -10 % (callgrind, Zelda II world map).
